## 4. Health and resilience (BACKEND)

### 4.1 `GET /v1/health` (anonymous, class `anon`, never needs a token)
Response 200 (`validateHealth`, example `fixtures/phase1/health.ok.json` and `health.paused.json`):
```jsonc
{ "ok": true, "checkedAt": "ISO", "cached": false,
  "services": {
    "auth": { "state": "ok|slow|paused|unreachable|unknown", "message": null | "plain English" },
    "git":  { "state": "ok|slow|paused|unreachable|unknown", "message": null | "plain English" },
    "ai":   { "state": "off|ready|budget_exhausted|no_key|unknown", "store": "memory|supabase", "message": null | "..." } },
  "message": null | "the first plain message that needs a human" }
```
* `ok` is true exactly when `auth` and `git` are `ok` or `slow` (the AI state never makes it false). `message` is null when `ok`.
* Checks run in parallel, each with a `STUDIO_HEALTH_TIMEOUT_MS` (default 3000) abort; the result is cached in memory per instance for `STUDIO_HEALTH_TTL_SECONDS` (default 30), so hammering the route cannot hammer Supabase or GitHub. Concurrent requests share ONE in-flight check.
* auth: dev mode -> `ok`. Otherwise one GET to `<SUPABASE_URL>/auth/v1/health` with the public `apikey`. Status 540, or a body matching `/paus/i` -> `paused`; network error, timeout or any 5xx -> `unreachable`; any other < 500 -> `ok` (`slow` when it took > 1500 ms).
* git: one `git.getHead(baseBranch)`; success -> `ok` (`slow` > 1500 ms); a `GitError` or timeout -> `unreachable`.
* ai: from the AI service (`disabled`->`off`, `no_key`, `budget_exhausted`, else `ready`) and the active store kind.
* Never returns a URL, key, error text from upstream, or a count of anything. Messages are fixed templates:
  * paused: "Sign-in is paused because the Studio database has been idle. An admin can wake it from the Supabase dashboard (Restore project)."
  * auth unreachable: "Studio cannot reach its sign-in service right now. Your edits on this page are safe. Try again in a minute."
  * git unreachable: "Studio cannot reach GitHub right now. You can keep editing; saving will work again when it is back."
* No audit entry per call (it is polled); the rate limiter still applies.

### 4.2 Plain messages when Supabase is down
* New error code `service_unavailable` (HTTP 503), `details: { "service": "auth" }`, message "Studio cannot reach its sign-in service right now. Your edits on this page are safe. Try again in a minute." `handler.js` throws it where it threw `upstream_error` for the role lookup ("The people list is unavailable."), and for `auth.verify` failures that are network failures (not bad tokens: those stay `unauthorized`). `errors.js` gains the code; the docs list in 14 is updated by the integrator.
* Login page (`studio/login/`): before sending a code it calls `GET /v1/health` (best effort, 2 s); if `services.auth.state` is `paused` or `unreachable`, or a Supabase call fails with a network error or 5xx, it shows the message above in an `aria-live` region and keeps the form usable. No third-party script, text via `textContent`.
* Overlay data for EDIT: `api-client` sees `error.code === "service_unavailable"` and `details.service`; EDIT shows the message in the Account panel and a toast. EDIT also shows `GET /v1/health` in Help (section 9.4).

### 4.3 GitHub provider: graceful label failure
`ensureLabels` / label POSTs must never fail PR creation or update. On any non-2xx other than "already exists" (422): log once through the audit sink as `{action:"label.failed"}` (no body), continue, and set `labelsApplied:false` on the returned `Pr`. Because `merge()` currently refuses a PR without the `studio-draft` label, the "is this a Studio draft" test becomes: `head ref starts with "studio/"` AND `!fromFork` AND `base === baseBranch` AND the Studio marker is in the PR body (see `services/pr-text.js`), AND (the label is present OR `labelsApplied` could not be written). A PR from any other branch, or `studio/...` without the marker, is still refused. Tests: refused (non-studio branch with marker), refused (studio branch without marker and label), accepted (marker, label write returned 403), accepted (marker + label).
The GitHub App permission note in the runbook says plainly: Issues: Read and write is needed for labels; without it everything works but PRs carry no labels.

### 4.4 Sign-in e-mail (runbook text only)
Runbook 4c.1 states: Supabase's built-in e-mail is rate-limited and only for testing; for real use set up custom SMTP in Supabase (Authentication > SMTP) with a transactional provider; the "email link" sign-in already works without SMTP codes (PR #13); the acceptance check is "20 codes arrive within 60 seconds" and is Teo's manual test.

## 5. Status board (REVIEW)

### 5.1 `GET /v1/board` (any role, class `read`)
Response 200 (`validateBoard`, `fixtures/phase1/board.json`):
```jsonc
{ "generatedAt": "ISO",
  "live": { "number": 52, "title": "...", "mergedAt": "ISO", "sha": "<40hex>", "url": "...", "by": { "name": "Molly" }, "settling": true } | null,
  "waiting":  [BoardItem],     // drafts that are ready (submitted) and not merged
  "restored": [BoardItem],     // merged revert drafts (HistoryItem.revertOf != null) of the last 30 days, max 10
  "mine":     [BoardItem],     // the caller's own open drafts (any state)
  "othersWaiting": 0 }         // editors only: how many OTHER people's drafts wait (count only)
BoardItem = { "id": "<draft id>", "number": 57, "title": "...", "url": "...", "reviewLink": string|null,
  "step": "editing|waiting_for_checks|checks_failed|waiting_for_approval|ready_to_publish|published|restored",
  "stepLabel": "plain English, <= 80", "author": { "name": "Amelia" }, "updatedAt": "ISO",
  "changeCount": 3 | null, "mine": false, "canReview": true, "canPublish": true }
```
* `live` = the newest item of `history.listHistory(ctx,{limit:1})` that is not a revert-in-progress; `settling` = merged less than `STUDIO_SETTLING_MINUTES` (default 10) ago: the UI says "Published. The site updates in a few minutes."
* Visibility: approvers/admins see every ready draft in `waiting`; editors see only their own there plus `othersWaiting` (count). `mine` is always the caller's own.
* Step table (first match): draft state `draft` -> `editing` "Still being edited"; `ready` and checks `none|pending` -> `waiting_for_checks` "Safety checks are running"; checks `failure` -> `checks_failed` "Safety checks need attention"; `ready` + `success` and `canPublish` for the caller -> `ready_to_publish` "Ready for you to approve"; otherwise `waiting_for_approval` "Waiting for approval". Merged items: `published` "Live"; reverts: `restored` "Restored".
* Built from the existing `services/drafts.listDrafts` and `services/history.listHistory`; cached in memory 15 s per `role:userKey`. Any upstream failure returns 502 `upstream_error`, never a partial board.
* `changeCount`: from a `Studio-Changes: N` marker REVIEW adds to the PR body (`pr-text.js`); `null` when unknown (older PRs).
* Overlay: new panel `status` (REVIEW, `order: 8`, title "Status"), refreshed on open and every 60 s while open; palette source `status.waiting` ("Waiting for approval: <title>") jumping to the review screen.

## 6. "What will change" screen (REVIEW)

### 6.1 `GET /v1/drafts/:id/review` (owner or approver/admin, class `read`)
Response 200 (`validateReview`, `fixtures/phase1/review.json`):
```jsonc
{ "draft": Draft,                       // the existing Draft shape (7.4 of DESIGN.md)
  "generatedAt": "ISO", "headSha": "<40hex>",       // the approver sends this back as expectedHeadSha
  "summary": "2 changes on 1 page",
  "items": [ ReviewItem ],              // ids r1..rN in order, one per patch op, <= 200
  "gates": { "checks": "none|pending|success|failure", "canPublish": true,
             "blockers": [ { "reason": "checks_pending|checks_failed|not_mergeable|draft_state|self_publish|head_changed|role", "message": "plain English" } ] },
  "sideBySide": null | { "productionUrl": "...", "draftUrl": "...", "pagePath": "/about/" } }
ReviewItem = { "id": "r1", "file": "src/_data/hero.json", "path": "/headlineMain", "op": "replace|add|remove|move",
  "kind": "text|image|link|color|toggle|section|list|page", "label": "Hero > Headline", "where": "Home page",
  "line": "Changes the Home page headline from \"...\" to \"...\".",           // ALWAYS present, plain English, <= 400
  "before": { "text": "...", "truncated": false, "image": null } | null,  "after": { ... } | null,   // production vs draft, each <= 2000 chars
  "pageUrl": "/" | "/about/" | null, "attention": "none|link|image|hidden|legal" }
```
* **Every patch op yields a line** (acceptance test): REVIEW extends `validate/describe.js` so `describe(op, ctx)` returns `{ line, before, after, where, pageUrl, attention }` for replace/add/remove/move on every kind in the schema; a property test loops over every field of the schema, builds each op type and asserts non-empty `line`, valid shapes, truncation, and no markup characters surviving into a field that the overlay will render (the overlay still uses `textContent`).
* `attention`: `link` when an address changes, `image` when a picture is replaced, `hidden` when a section is switched off, `legal` when the file is the privacy/legal page or the contact email: the approver screen lists these first under "Look at these carefully".
* `gates.blockers` reuse the exact conditions of `services/drafts.publishDraft` (extract one `publishBlockers(ctx, draft)` function; `publishDraft` and this route both call it so they cannot disagree). `canPublish` is true exactly when `blockers` is empty.
* `sideBySide` is non-null ONLY when `config.review.previewEmbed` AND `draft.previewUrl` AND `config.review.siteUrl` are all set. Default off (P5). When null, the screen shows the text before/after list only and says "A picture of the draft is not available yet".
* Pictures: before/after show the file name and, for an upload, its size in pixels and KB (from the draft head, via the existing image header reader in `validate/images.js`); no image bytes are sent.

### 6.2 "Approve and publish"
One button, calls the EXISTING `POST /v1/drafts/:id/publish` with `{ idempotencyKey, expectedHeadSha: review.headSha }`. No new route and no gate is removed or weakened: CI green, `studio-scope` green, a second person, `ready` state, head unchanged, mergeable. When `blockers` is non-empty the button is disabled and the blockers are listed in plain words. A 409 `not_ready` or `draft_moved` after the click refreshes the screen and says what changed.
Overlay: panel `review` (REVIEW) opened from the board, from the Changes panel ("Open review screen") and from the deep link `#review=<draftId>` (handled when Studio is ready and the person is signed in). Focus moves to the panel title; the summary is read through `aria-live`.

## 7. Send for review (REVIEW; Git provider methods by BACKEND)

### 7.1 `GET /v1/people/approvers` (any role, class `read`)
`{ "approvers": [ { "id": "molly", "displayName": "Molly", "role": "approver|admin", "notify": "github|manual" } ] }` (`validateApprovers`). Source: `config.review.reviewers` (env `STUDIO_REVIEWERS`, a JSON array `[{ "id": "molly", "name": "Molly", "github": "mollygh" | null, "role": "approver" }]`, at most 10; `id` `[a-z0-9-]{1,30}`, `github` `[A-Za-z0-9-]{1,39}`). `notify` is `github` when a login is set, else `manual`. Never returns e-mail addresses or logins. The author is never listed as their own reviewer. Empty when the variable is unset.

### 7.2 `POST /v1/drafts/:id/submit` (owner, class `write`)
Request: `{ "idempotencyKey": "<uuid>", "reviewerId": "molly" | null }` (`reviewerId` is new and optional; unknown id -> 400).
Response 200 (`validateSubmitResponse`, `submit.github.json`, `submit.manual.json`): the old `{ draft }` PLUS
```jsonc
{ "draft": Draft, "reviewLink": "<base>/?studio=1#review=<draftId>" | null,
  "notified": { "via": "github|none", "reviewer": { "displayName": "Molly" } | null,
                "reason": null | "no_reviewer_chosen|no_github_login|github_refused|github_unavailable" },
  "message": "plain English sentence the dialog shows" }
```
* `<base>` = `STUDIO_REVIEW_BASE_URL` if set, else `draft.previewUrl`, else `config.appUrl`; null when none is configured. Always `https` or localhost.
* Order: mark the PR ready (existing) -> if a reviewer with a GitHub login was chosen, `git.requestReviewers(prNumber, [login])`. A failure there NEVER fails the submit: it returns `via:"none"` with `reason: "github_refused"` (e.g. not a collaborator) or `"github_unavailable"` and the dialog falls back to copy-link. Idempotent: a replayed submit does not re-notify.
* The audit entry gets `outcome` and `reviewer` (id only) but no login or e-mail.

### 7.3 Git provider additions (BACKEND implements; REVIEW codes against this and tests with a thin fake)
`requestReviewers(prNumber, logins[]) -> { requested: string[] }` (GitHub: `POST /pulls/{n}/requested_reviewers`; mock-memory records them and lets a test make it fail with a `GitError`). Add the name to `METHODS` in `providers/git/interface.js` and a case to the provider contract test. No other new provider method is needed.

### 7.4 Overlay

## 8. Content rule engine (EDIT)

### 8.1 Location and API
`studio/content-rules/` (UMD, pure, no fs/DOM/network/eval/Date/Math.random, ES2019, runs in browsers and Node):
```
engine.js   register(rule), run(input) -> Report, rules(), ENGINE_VERSION          (skeleton exists)
rules.js    registers every rule below                                             (EDIT writes)
index.js    Node entry: the engine with rules.js registered                        (exists)
facts-node.js   buildFacts(root, opts) -> Facts        Node only (fs). NOT in the overlay bundle.
field-roles.json  which schema fields are SEO title / description / link label / etc. (data, section 8.3)
baseline.json   { "blocked": ["key", ...] }  known existing block findings (the CI ratchet, section 8.5)
```
`run(input)`: `input = { files: { fileKey: data }, schema, facts, only? }` where `files` has the same shape as `content.json.files[*].data` (data files by stem, pages as `pages:<slug>` with `_body`), `schema` is `studio-schema.json`, `facts` is below. Returns the `Report` of `validateRuleReport` (`fixtures/phase1/rule-report.json`): `{ engineVersion:1, ranRules, findings:[Finding], counts }`. `Finding = { key: "<rule>|<file path>|<json pointer>", rule, severity: "block|warn|info", file, path, message (plain English, <= 300), hint, fix: null|{kind: "edit-field|shorten|pick-image|reword-link"}, data }`. Findings are sorted by severity then key; keys are unique. A rule is `{ id, severity, title, check(ctx) -> [{ file, path, message, hint?, fix?, data?, severity? }] }`; `ctx = { files, schema, facts, ...helpers }` (EDIT may add pure helpers: `walk`, `fieldAt`, `altPairs`, `linkPairs`). A rule that throws is reported as an engine error by the CALLER (the engine does not swallow it): tests make sure no rule throws on any current repo file or on the hostile fixtures.

### 8.2 Facts (the only non-data input)
```jsonc
Facts = { "routes": ["/", "/about/", ...],          // every built page path, trailing slash
          "anchors": { "/": ["how", "faq"] },        // element ids per route that links may target
          "redirectFrom": ["/old-path"],             // redirect sources (a link to one is "info", not "block")
          "images": { "story-5.jpg": { "bytes": 412345, "width": 1600, "height": 900 } },   // files in images/
          "pages": { "/": { "images": ["story-5.jpg"], "bytes": 1850000 } } }               // referenced pictures per route
```
Two producers, ONE builder: `facts-node.js#buildFacts(root, { site? })` derives it from the repo (routes from `src/pages` permalinks, `src/index.njk` and the fixed tool pages listed in `scripts/copy-allowlist.json`; anchors from the built `_site` when `site` is passed, else from reserved ids; image sizes with the existing `image-size`/`scripts/lib/image-rules.js` readers). `studio/markers/snapshot.js` (edit builds only) embeds `facts` (compact, <= 40 KB) in `content.json` as the new top-level key `facts`; `schemaVersion` stays 1 (additive). The overlay adds uploads staged in the browser to `facts.images` before running. If `content.json` has no `facts` the overlay skips the facts-based rules and the panel says so. A test proves `buildFacts` routes equal the routes of a real build's sitemap.

### 8.3 Field roles (derive, do not hand-list)
Alt text and decorative pairs come from the schema the same way `scripts/check-cms.js` pairs them (picture field + sibling alt + sibling decorative); a guard proves every `x.rule: image` field is covered by a pair or by `scripts/alt-exemptions.json`. SEO title/description fields, link-label fields and markdown bodies are identified by `field-roles.json` (a small committed map keyed by `file:field-name` or `*:name`); `check-content-rules` fails when the schema has a field named like one of those roles (`pageTitle`, `metaDescription`, `ogDescription`, `socialTitle`, `title`, `description`, `label`, `text`, `cta*`) that `field-roles.json` neither maps nor lists as `ignore`, so a new field cannot silently escape the rules.

### 8.4 Rules (ids, severity, thresholds; messages are plain English and name the thing)
| id | sev | flags |
|---|---|---|
| `alt-missing` | block | a picture that is not decorative has an empty description (after trim) |
| `alt-weak` | warn | description is under 5 or over 150 characters, equals the file name/stem, or starts "image of / picture of / photo of" |
| `title-length` | warn | an SEO title is over 60 or under 15 characters |
| `description-length` | warn | a meta description is over 160 or under 70 (social description: over 200 or under 40) |
| `duplicate-text` | warn | two files share the same title or description (case/space-insensitive); two FAQ questions equal; two list items with identical headings |
| `vague-link-text` | warn | a link label is one of: click here, here, read more, learn more, more, link, this, find out more (case/space/punctuation-insensitive) |
| `broken-internal-link` | block | a link value starting with `/` whose path (query and `#` removed) is neither in `facts.routes` nor `facts.redirectFrom`; a `#id` link whose id is not in `facts.anchors[route]` (`info` when the route is unknown) |
| `heading-skip` | warn | in a markdown value: a heading level jumps by more than one, or an H1 appears (the page title is already the H1) |
| `image-heavy` | warn | a referenced picture is over 600 KB or over 3000 px wide |
| `page-weight` | warn | the pictures a route uses add up to over 3 MB (`facts.pages`) |

Panel wording (checked by the guard): header "Check my changes", sub-line "These checks look at your words, links and pictures. They are not a full accessibility audit." The strings `WCAG` and `accessible` never appear as a claim about the result. Each finding has **Fix** (jumps to the field with `studio.ui.editRef`, `fix.kind` decides focus/hint) and, for `warn`/`info` only, **Ignore** (kept per draft in `localStorage` with try/catch; never sent anywhere; CI ignores it).

### 8.5 The same engine in CI
`studio/guards/check-content-rules.js` (auto-run by `check:studio`): loads the repo's data and pages, `buildFacts(root)`, runs the engine, prints warnings, and FAILS (exit 1) for every `block` finding whose key is not in `baseline.json`, and for every baseline key that no longer occurs (ratchet down). `--json` prints the Report so tests can compare. It runs on Studio draft PRs too (`Build and guards` is a required check), so a `block` finding in a draft turns CI red: the overlay therefore refuses "Send for review" while `block` findings exist and says why ("Fix these first; they would stop your change from going live"). Saving a draft is never blocked. `warn` findings never fail CI.
**Parity proof (test + selftest):** `p1-edit/ci-parity.test.js` seeds a set of bad drafts (one per rule, plus a good one) in a temp workspace, runs the guard `--json` and the overlay-loaded engine (`studio/tests/overlay/load.js`) on the same content and facts, and asserts the same `key`s and severities. Selftest scenarios break each rule's check and the baseline ratchet and expect the guard to fail.
Pre-existing findings: the overlay runs the engine on the base content too and marks findings that already exist there as "Already on the live site" so a founder is not blamed for them.

## 10. AI usage store, estimate, recent (BACKEND)

### 10.1 Store interface (async; replaces the sync `budget.js` four methods)
```
BudgetStore { kind: "memory"|"supabase",
  reserve({ day, tokens, userId, caps:{ requests, tokens, userRequests } }) -> { ok, reason: null|"global_requests"|"global_tokens"|"user_requests", global:{requests,tokens}, user:{requests,tokens} }
  settle({ day, reserved, actual, userId, countRequest })   // always adds the real tokens; countRequest:false gives the request back
  release({ day, reserved, userId })                         // the call failed before any model answer: nothing spent
  snapshot({ day, userId }) -> { global:{requests,tokens,requestsLimit,tokensLimit}, user:{requests,tokens,requestsLimit} }
  recordRequest({ userId, id, mode, kind, tokens }) ; attachAccept({ userId, id, accepted, total, prNumber }) ; recent({ userId, limit }) -> [RecentItem] }
```
`createMemoryBudget` keeps its current numbers and gains the per-user counters and a 20-entry recent list per user; `createSupabaseBudget({ url, anonKey, fetch })` is bound per request to the caller's JWT (`ctx.token`) and calls the RPC functions below through PostgREST (`/rest/v1/rpc/<fn>`) - the API never holds a service key. Selection: `STUDIO_AI_BUDGET_STORE=memory` (default) or `supabase`. If an RPC answers 404 (function not applied) or fails, that request uses the memory store, a `usage.store_fallback` line goes to the log, and `status.usage.store` shows `memory`. Never fail open: with the Supabase store down the memory caps still apply.

### 10.2 `studio/sql/003_studio_ai_usage.sql` (presented for human review, NEVER applied by code; header says so like 001/002)
Leaves 002 untouched. Adds: table `studio_ai_user_usage(day date, user_id uuid, requests int, tokens bigint, primary key(day, user_id))`; table `studio_ai_requests(id text primary key, user_id uuid, at timestamptz default now(), mode text, kind text, tokens integer, accepted integer, total integer, pr_number integer)`; both with row level security ON and NO policies, `revoke all from anon, authenticated`. Functions, all `security definer`, `set search_path = public`, each beginning with the active-role check used in 002 (`auth.uid()` + `studio_roles.active`):
`studio_ai_reserve2(p_day, p_tokens, p_max_requests, p_max_tokens, p_user_max_requests) returns table(ok boolean, reason text, g_requests int, g_tokens bigint, u_requests int, u_tokens bigint)` (one transaction: insert-on-conflict the two rows, then UPDATE global WHERE caps hold, then UPDATE user WHERE cap holds, rolling back the global bump if the user cap refuses; lock order global then user), `studio_ai_settle2(p_day, p_reserved, p_actual, p_count_request boolean)`, `studio_ai_release2(p_day, p_tokens)`, `studio_ai_snapshot2(p_day)`, `studio_ai_record(p_id, p_mode, p_kind, p_tokens)` (also deletes the caller's rows older than 30 days), `studio_ai_attach(p_id, p_accepted, p_total, p_pr)`, `studio_ai_recent(p_limit)` (own rows only, <= 20). No instruction text, page content or names are ever stored. A static test parses the file and asserts: every function is `security definer` with a pinned `search_path` and the role check, RLS is enabled with no policy on both tables, and no statement grants to `anon`.
